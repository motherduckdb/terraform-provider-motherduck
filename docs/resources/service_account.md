# motherduck_service_account (Resource)

Create a non-human account for a pipeline, environment, or application reader.
This resource uses `MOTHERDUCK_ADMIN_TOKEN`. Configure SQL ownership separately
by running the warehouse root with this account's read-write token.

## Usage and lifecycle

The username is the resource identity. It must be 3 to 255 UTF-16 code units,
start with a letter, and continue with letters, ASCII digits, or underscores.
MotherDuck compares usernames case-insensitively, so changing only the letter
case updates the resource in place without an API call. Any other rename
replaces the account.

Some older service accounts have legacy usernames that also contain hyphens,
at signs, or periods, such as `mdw-writer@motherduck-com`. Import such an
account by its username to manage it. MotherDuck no longer creates accounts
with these characters, so a plan that would create or rename to one fails.

`description` is sent only when MotherDuck creates the account. MotherDuck has
no API to read or change it, so the provider fails the plan when the configured
description changes instead of replacing the account and deleting its data. A
rename still replaces the account, and the new account gets the configured
description. An imported account adopts the configured description once,
without verification.

Removing `description` from the configuration clears it from state with no API
call, and the account keeps the description it was created with. A description
added back later is adopted once, like after import. To record a different
description without recreating the account, run `terraform state rm` and then
`terraform import` for the account. MotherDuck still keeps the original
description.

Free, Lite, and not yet started trial organizations can have at most two
service accounts. Business organizations and active free trials have no such
limit.

Create tokens with `motherduck_access_token` and configure its compute with
`motherduck_duckling_config`. Account creation does not switch the provider's
SQL identity or move existing databases to the new account.

## Service accounts only

`DELETE /v1/users/{username}` deletes any user, so the provider checks the
organization user listing before it trusts a username. Refresh, import, and
destroy fail with an error when the username belongs to a human user, and the
resource stays in state. Remove such a resource with `terraform state rm`.

Refresh, import, and destroy list the organization's users, so the admin token
needs the `member_management.view_all_members` privilege. The built-in
`admin`, `builder`, and `explorer` roles include it. The listing pages by
offset and can skip a user while other users are created or deleted. When the
username is missing from the listing, the provider checks
`GET /v1/users/{username}/instances`. A not-found answer means the account is
gone, so refresh removes it from state and destroy treats it as deleted. When
the account still exists, the provider fails with an error, keeps the state,
and sends no delete. Retry the operation.

**Deleting the service account deletes the data it owns.** Destroy downstream
warehouses with their original writer credential before removing their account.
Revoke custom-role grants before an external account deletion. Recreating the
same username creates a new account identity and may leave old role assignments
that require service-side cleanup. See [role deletion order](role.md#deletion-order).
Import by username when Terraform should own an existing account's lifecycle.

See [environment bootstrap](../guides/environments.md) and
[customer-facing readers](../guides/customer-facing-analytics.md).

## Example Usage

```terraform
resource "motherduck_service_account" "app" {
  username = "analytics_app"
}

resource "motherduck_access_token" "app" {
  username   = motherduck_service_account.app.username
  name       = "terraform-managed"
  token_type = "read_write"
  ttl        = 2592000
}
```
